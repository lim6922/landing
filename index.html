# 랜딩 페이지 초안 설명 (HTML 재작성 반영 버전) ## 목적 이 랜딩 페이지는 특정 하나의 앱을 메인 제품으로 두는 구조가 아니라, 여러 앱을 같은 레벨에서 소개하는 **앱 카탈로그형 페이지**를 목표로 한다. 즉, `Workspace Hub`도 여러 앱 중 하나이며, `Canvas Workspace`, `Kanvan Calendar`, `Wiki Builder`, `Textlist`, `Writer’s Clock`과 동일한 수준에서 노출된다. 이 페이지의 핵심 목적은 다음과 같다. - 현재 존재하는 앱들을 외부 사용자에게 간결하게 소개한다. - 각 앱으로 바로 진입할 수 있는 링크를 제공한다. - GitHub, 기술 블로그, 문서 링크를 앱별로 연결할 수 있게 한다. - 이후 새로운 앱이 추가될 때마다 데이터만 추가해서 확장할 수 있게 한다. --- ## 이번 재작성에서 반영한 핵심 변경점 이번 HTML 재작성에서는 다음 두 가지 요구를 직접 반영했다. 1. **topbar 다음에 바로 앱 section이 오도록 구조 변경** 2. **카드 내부에 링크 정보가 있으면 `상세 보기` 버튼에서 그 링크를 버튼 형태로 연결** 즉, 기존의 설명 중심 배치에서 벗어나, - 첫 화면에서 바로 앱이 눈에 들어오도록 하고, - 링크는 카드에 직접 과하게 노출하지 않고, - `상세 보기` 모달 안에서 링크 허브처럼 정리되도록 바꿨다. --- ## 최종 페이지 구조 재작성된 `landing.html`의 구조는 다음과 같다. ### 1. Topbar 포함 요소: - 브랜드명 - 한 줄 소개 - GitHub 버튼 - 기술 블로그 버튼 역할: - 페이지 정체성 표시 - 외부 공개 페이지임을 즉시 전달 --- ### 2. Apps Section (첫 화면 핵심) `topbar` 다음에 바로 오는 가장 중요한 섹션이다. 포함 요소: - 섹션 제목 - 짧은 안내 문장 - 제품 카드 그리드 이 구조로 변경한 이유는 다음과 같다. - 방문자가 페이지에 들어오자마자 앱을 볼 수 있다. - 설명보다 앱 목록이 먼저 시야에 들어온다. - "앱을 꾸준히 추가하는 허브"라는 목적에 더 잘 맞는다. 즉, - **설명은 보조 요소** - **앱 목록은 메인 요소** 가 되도록 위계를 재정렬했다. --- ### 3. Hero (하단 보조 설명) 기존에는 hero가 상단에 크게 오는 구조였지만, 재작성 버전에서는 hero를 앱 목록 아래로 이동했다. 역할: - 전체 앱군의 방향을 짧게 설명 - 브랜드 톤 유지 - 첫 화면에서 앱을 가리지 않도록 보조 정보로만 사용 이제 hero는 페이지의 주인공이 아니라, **앱을 먼저 본 뒤 읽는 짧은 보조 소개** 역할을 한다. --- ### 4. Footer Box 하단에는 다음만 남긴다. - 새로운 앱이 계속 추가된다는 메시지 - GitHub 링크 - 기술 블로그 링크 즉, CTA(call to action)를 단순하게 유지한다. --- ## 앱 카드 구조 각 앱 카드는 다음 정보만 담는다. - 아이콘 - 앱 이름 - 짧은 설명 - 태그 2~3개 - 카드 링크 힌트(optional) - 버튼 - `열기` - `상세 보기` 이 구조의 핵심은 **카드를 너무 복잡하게 만들지 않는 것**이다. 카드는 빠르게 훑는 용도이므로, 외부 링크를 카드 안에서 전부 버튼으로 노출하지 않고, 필요한 정보는 힌트만 보여주고 모달로 넘긴다. --- ## 카드 링크 정보 → 상세 보기 연결 구조 이번 재작성에서 가장 중요한 기능 개선이다. ### 목적 앱 카드 설명 내부에 링크 성격의 정보가 있을 경우, 그 정보를 그냥 텍스트로만 끝내지 않고, `상세 보기` 버튼에서 실제 연결 가능한 링크 버튼으로 이어지게 만든다. ### 적용 방식 앱 데이터에 `cardLinks` 필드를 둔다. 예: ```js cardLinks: [ { type: "blog", label: "기술 글 연결 가능", href: "https://..." }, { type: "github", label: "GitHub 연결 가능", href: "https://..." } ] ``` ### 카드에서의 동작 카드에서는 이 정보를 `link chip`처럼 요약해서 보여준다. 예: - 기술 글 연결 가능 - GitHub 연결 가능 즉 카드에서는 “이 앱에 추가 링크가 있다”는 사실만 직관적으로 보이게 한다. ### 상세 보기에서의 동작 `상세 보기` 모달을 열면, `links`와 `cardLinks`를 합쳐 실제 링크 버튼을 자동 생성한다. 예: - 바로 열기 - GitHub - 기술 글 - 문서 즉, - **카드 = 링크 존재 힌트** - **상세 보기 = 실제 링크 허브** 역할 분리를 한다. --- ## 링크 처리 규칙 각 앱은 최대 두 종류의 링크 필드를 가진다. ### 1. `links` 기본 링크 모음 ```js links: { open: "", github: "", blog: "", docs: "" } ``` ### 2. `cardLinks` 카드 안에서 힌트로 보여줄 링크 정보 ```js cardLinks: [ { type: "blog", label: "기술 글 연결 가능", href: "..." } ] ``` ### UI 규칙 | 필드 | 카드 | 상세 보기 | |------|------|-----------| | `links.open` | `열기` 버튼 | `바로 열기` 버튼 | | `links.github` | 표시 안 함 | 버튼 노출 | | `links.blog` | 표시 안 함 | 버튼 노출 | | `links.docs` | 표시 안 함 | 버튼 노출 | | `cardLinks` | 힌트 칩 노출 | 실제 버튼으로 연결 | 이 구조를 쓰면, 카드는 단순하게 유지하면서도, 상세 보기에서는 링크를 충분히 제공할 수 있다. --- ## 상세 보기 모달 구조 모달은 다음 내용을 담는다. - 앱 이름 - 상세 설명(summary) - 태그 - 추천 사용 상황(useCases) - 같이 보기 좋은 앱(related) - 링크 버튼 허브 즉, - **카드 = 스캔용** - **모달 = 이해/확장용** 역할을 분리했다. 모달 안에서는 카드에서 힌트로만 보였던 링크 정보를 실제 버튼으로 바꾸어, 사용자가 바로 이동할 수 있게 한다. --- ## Workspace Hub의 위치 이번 구조에서도 `Workspace Hub`는 특별한 중심이 아니다. 다음 앱들과 동일한 레벨로 카드에 포함된다. - Workspace Hub - Canvas Workspace - Kanvan Calendar - Wiki Builder - Textlist - Writer’s Clock 이 방식의 장점은 다음과 같다. - 특정 앱이 메인이라는 인상을 주지 않는다. - 사용자가 목적에 따라 직접 앱을 고를 수 있다. - 이후 새로운 앱이 추가되어도 구조가 흔들리지 않는다. - 앱 카탈로그 페이지 목적과 잘 맞는다. --- ## 데이터 구조 설명 랜딩 페이지의 확장성을 위해 앱 정보는 배열 데이터로 관리한다. 예시 구조: ```js { id: "canvas", name: "Canvas Workspace", icon: "ri-layout-grid-fill", short: "아이디어를 공간 위에 배치하고 연결하는 시각적 보드", summary: "브레인스토밍, 관계도 작성, 시각적 사고 정리에 적합한 보드형 앱입니다.", tags: ["브레인스토밍", "시각화", "구조화"], useCases: [ "아이디어를 자유롭게 배치하고 싶을 때", "연결 관계를 시각적으로 정리하고 싶을 때" ], related: ["wiki", "textlist"], cardLinks: [ { type: "blog", label: "기술 글 연결 가능", href: "..." } ], links: { open: "/canvas.html", github: "", blog: "", docs: "" } } ``` ### 필드 역할 - `id`: 제품 고유 식별자 - `name`: 카드/모달 표시 이름 - `icon`: Remix Icon 클래스명 - `short`: 카드용 짧은 설명 - `summary`: 모달용 상세 설명 - `tags`: 카드 하단 태그 - `useCases`: 추천 사용 상황 목록 - `related`: 같이 보기 좋은 앱 id 목록 - `cardLinks`: 카드 힌트 + 상세 보기 링크 확장용 정보 - `links`: 기본 외부 링크 모음 이 구조를 사용하면 새 앱을 추가할 때 HTML을 고치지 않고, 데이터만 추가해도 카드와 상세 모달이 자동 생성된다. --- ## 디자인 방향 랜딩 페이지는 기존 앱 허브의 밝은 톤을 유지한다. 기본 원칙: - 밝은 배경 - indigo + sky 계열 포인트 컬러 - 둥근 카드 - 가벼운 그림자 - 읽기 쉬운 간격 다만 위계는 조정했다. - 이전: 설명 중심 - 현재: 앱 카드 중심 즉, **기존 허브의 감성은 유지하면서도, 정보 우선순위를 앱 쪽으로 재배치한 형태**다. --- ## 아이콘 시스템 현재 랜딩 페이지는 **Remix Icon**을 사용한다. 사용 방식: ```html ``` 예: ```html ``` 아이콘 검색 및 예시는 공식 사이트에서 확인한다. - 공식 사이트: https://remixicon.com/ 새 앱 추가 시에는 이 사이트에서 아이콘을 검색하고, 적절한 클래스명을 `icon` 필드에 넣으면 된다. --- ## 확장 방식 이 랜딩 페이지의 가장 중요한 설계 원칙은 **지속적인 앱 추가**다. ### 새 앱 추가 절차 1. `PRODUCTS` 배열에 새 객체 추가 2. `name`, `icon`, `short`, `links.open` 입력 3. 필요하면 `summary`, `useCases`, `github`, `blog`, `docs` 추가 4. 카드에 링크 힌트를 보여주고 싶으면 `cardLinks` 추가 이렇게 하면 별도의 HTML 수정 없이 카드와 모달이 자동 반영된다. ### 추천 파일 구조 ```text landing/ ├─ landing.html ├─ landing.css ├─ landing.js └─ products.js ``` 장기적으로는 `PRODUCTS`를 별도 파일로 분리하는 것이 가장 좋다. 이유: - 새 앱 추가가 쉬워진다. - 설명 데이터와 UI 로직이 분리된다. - 유지보수가 단순해진다. --- ## 배포 제언 이 페이지는 정적 HTML/CSS/JS만으로 충분하다. 따라서 배포는 다음 두 방식이 모두 가능하다. ### GitHub Pages 적합한 경우: - 빠르게 시작하고 싶을 때 - 정적 페이지로만 운영할 때 - 저장소 중심 공개가 목적일 때 ### Cloudflare Pages 적합한 경우: - 커스텀 도메인을 편하게 붙이고 싶을 때 - 추후 폼, 간단한 동적 기능, 리다이렉트 등을 붙일 가능성이 있을 때 - 제품 수가 계속 늘고 운영 유연성이 중요할 때 현재 요구사항처럼 제품이 계속 늘어날 예정이라면 Cloudflare Pages 쪽이 조금 더 유리하다. --- ## 요약 이번 재작성 버전의 핵심은 다음과 같다. - `topbar` 다음에 바로 앱 section이 온다. - 앱이 첫 화면에서 가장 먼저 보인다. - hero는 하단의 보조 설명으로 이동했다. - `Workspace Hub`도 여러 앱 중 하나로 동일 레벨에 놓인다. - 카드 설명 안의 링크 정보는 `cardLinks`로 관리한다. - 카드에서는 링크 존재를 힌트로 보여주고, - `상세 보기` 모달에서는 실제 연결 버튼으로 바꿔 노출한다. - 새로운 앱은 데이터만 추가해 확장할 수 있다. 즉, 이 페이지는 단순한 소개 페이지가 아니라, **계속 늘어나는 앱들을 직관적으로 보여주고, 상세 보기 안에서 링크까지 연결하는 외부용 앱 카탈로그**다.
