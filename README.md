# 랜딩 페이지 초안 설명

## 목적

이 랜딩 페이지는 특정 하나의 앱을 메인 제품으로 두는 구조가 아니라, 여러 앱을 같은 레벨에서 소개하는 **앱 카탈로그형 페이지**를 목표로 한다.

즉, `Workspace Hub`도 여러 앱 중 하나이며, `Canvas`, `Kanvan Calendar`, `Wiki Builder`, `Textlist`, `Writer’s Clock`과 동일한 수준에서 노출된다.

이 페이지의 핵심 목적은 다음과 같다.

* 현재 존재하는 앱들을 외부 사용자에게 간결하게 소개한다.
* 각 앱으로 바로 진입할 수 있는 링크를 제공한다.
* GitHub, 기술 블로그, 문서 링크를 앱별로 연결할 수 있게 한다.
* 이후 새로운 앱이 추가될 때마다 데이터만 추가해서 확장할 수 있게 한다.

---

## 기본 방향

기존 내부용 `Workspace Shell`은 다음과 같은 역할을 함께 가지고 있다.

* 로그인
* sync 상태 표시
* 앱 전환
* iframe stage
* 축소 허브
* 레지스트리 관리
* 클라우드 워크스페이스 상태 관리

하지만 외부 공개용 랜딩 페이지에서는 이런 내부 운영 로직이 필요하지 않다.

따라서 외부용 랜딩은 다음 요소만 남긴다.

* 브랜드 헤더
* 짧은 소개(hero)
* 앱 카드 목록
* 앱별 상세 소개 모달
* 외부 링크(GitHub / 블로그 / 문서 / 앱 진입 링크)

이렇게 하면 페이지가 훨씬 단순해지고, 유지보수도 쉬워진다.

---

## 구조 개요

랜딩 페이지는 크게 5개 영역으로 구성한다.

### 1. 헤더

헤더는 브랜드와 외부 링크만 담는다.

포함 요소:

* 브랜드명
* 한 줄 소개
* GitHub 버튼
* 기술 블로그 버튼

목적:

* 페이지 정체성을 보여준다.
* 앱 설명보다 먼저 "이 페이지가 무엇인지"를 짧게 이해시키는 역할을 한다.

---

### 2. 히어로 섹션

히어로는 전체 앱군의 방향을 짧게 설명한다.

핵심 메시지:

* 생각, 문서, 일정, 텍스트를 각기 다른 앱으로 다룬다.
* 여러 앱은 서로 동등한 도구들이다.
* 새로운 앱이 계속 추가된다.

기존 허브의 복잡한 기능 설명보다는, 외부 사용자 입장에서 제품군의 성격을 이해하도록 짧게 정리한다.

---

### 3. 앱 카드 그리드

랜딩의 중심 영역이다.

각 앱 카드는 다음 정보만 담는다.

* 아이콘
* 앱 이름
* 짧은 설명
* 태그 2~3개
* `열기` 버튼
* `소개` 버튼

이 영역은 최대한 심플해야 한다.

이유:

* 앱 수가 늘어나도 레이아웃이 안정적이다.
* 사용자는 빠르게 훑고, 필요한 앱만 고를 수 있다.
* 카드 하나하나에 너무 많은 정보를 넣지 않아도 된다.

---

### 4. 앱 상세 소개 모달

카드를 눌렀을 때 앱별 세부 설명을 보여주는 영역이다.

모달에는 다음 내용을 넣는다.

* 앱 이름
* 더 긴 설명(summary)
* 추천 사용 상황(useCases)
* 같이 보기 좋은 앱(related)
* 외부 링크

  * 앱 열기
  * GitHub
  * 기술 글
  * 문서 링크

이 구조를 선택한 이유는 다음과 같다.

* 카드에는 최소 정보만 보여주고,
* 더 자세한 내용은 모달로 분리해 정보 밀도를 조절할 수 있다.

즉,

* **카드 = 스캔용**
* **모달 = 이해/설득용**

역할 분리를 한다.

---

### 5. 하단 안내 섹션

하단에는 짧은 메시지만 남긴다.

예:

* 새로운 앱이 계속 추가된다는 안내
* GitHub / 기술 블로그 링크

이 영역은 CTA(call to action) 역할을 한다.

## 앱 데이터 구조 설명

랜딩 페이지의 확장성을 위해 앱 정보는 코드에 하드코딩하지 않고, 하나의 배열 데이터로 관리한다.

예시 구조:

```js
const PRODUCTS = [
  {
    id: "canvas",
    name: "Canvas Workspace",
    icon: "ri-layout-grid-fill",
    short: "아이디어를 공간 위에 배치하고 연결하는 시각적 보드",
    summary: "브레인스토밍, 관계도 작성, 시각적 사고 정리에 적합한 보드형 앱입니다.",
    tags: ["브레인스토밍", "시각화", "구조화"],
    useCases: [
      "아이디어를 자유롭게 배치하고 싶을 때",
      "연결 관계를 시각적으로 정리하고 싶을 때"
    ],
    related: ["wiki", "textlist"],
    links: {
      open: "/canvas.html",
      github: "",
      blog: ""
    }
  }
];
```

### 필드 역할

* `id`: 제품 고유 식별자
* `name`: 카드와 모달에 표시될 이름
* `icon`: Remix Icon 클래스명
* `short`: 카드용 한 줄 설명
* `summary`: 모달용 상세 설명
* `tags`: 카드 하단 태그
* `useCases`: 추천 사용 상황 목록
* `related`: 같이 보기 좋은 앱 id 목록
* `links`: 외부 링크 모음

이 구조를 사용하면 새 앱을 추가할 때 HTML을 고칠 필요 없이, 배열에 객체 하나를 추가하는 것만으로 카드와 모달이 자동 생성된다.

## Workspace Hub를 포함하는 방식

이번 초안에서 중요한 점은 `Workspace Hub`가 **대표 메인**이 아니라 **여러 앱 중 하나**라는 것이다.

즉,

* `Workspace Hub`
* `Canvas Workspace`
* `Kanvan Calendar`
* `Wiki Builder`
* `Textlist`
* `Writer’s Clock`

이 모두 같은 레벨의 앱으로 카드에 노출된다.

이 방식의 장점은 다음과 같다.

* 특정 앱이 중심이라는 인상을 주지 않는다.
* 사용자가 목적에 따라 앱을 직접 선택할 수 있다.
* 이후 새로운 앱이 추가되어도 구조가 흔들리지 않는다.
* 앱 카탈로그라는 페이지 목적과 잘 맞는다.

---

## 링크 전략

각 앱은 최대 4종류 링크를 가질 수 있다.

* `open`: 앱 열기
* `github`: GitHub 저장소 또는 코드 링크
* `blog`: 기술 블로그 또는 소개 글
* `docs`: 문서 링크

이 중 없는 링크는 버튼을 숨긴다.

이렇게 하면 앱마다 정보 공개 수준이 달라도 같은 구조를 유지할 수 있다.

예를 들어,

* 어떤 앱은 `open`만 있을 수 있고,
* 어떤 앱은 `open + github + blog`를 모두 가질 수 있다.

---

## 디자인 방향

랜딩 페이지는 기존 앱 허브의 밝은 톤을 유지한다.

기본 원칙:

* 밝은 배경
* indigo + sky 계열 포인트 컬러
* 둥근 카드
* 가벼운 그림자
* 읽기 쉬운 간격

기존 내부 허브처럼 복잡한 상태 UI를 유지하지 않고, 카드 중심 구조만 유지한다.

즉, **기존 허브의 감성은 살리고 내부 운영 로직은 제거한 형태**다.

## 아이콘 시스템

현재 앱 허브는 **Remix Icon**을 사용한다.

사용 방식:

* CDN으로 css 로드
* 앱 데이터의 `icon` 필드에 클래스명 저장
* 카드/모달에서 그대로 렌더

예:

```html
<link href="https://cdn.jsdelivr.net/npm/remixicon@4.2.0/fonts/remixicon.css" rel="stylesheet">
```

```html
<i class="ri-book-open-line"></i>
<i class="ri-layout-grid-fill"></i>
```

아이콘 검색 및 예시는 공식 사이트에서 확인한다.

* 공식 사이트: [https://remixicon.com/](https://remixicon.com/)

새 앱 추가 시에는 이 사이트에서 아이콘을 검색하고, 적절한 클래스명을 `icon` 필드에 넣으면 된다.

## 확장 방식

이 랜딩 페이지의 가장 중요한 설계 원칙은 **지속적인 앱 추가**다.

### 새 앱 추가 절차

1. `PRODUCTS` 배열에 새 객체 추가
2. `name`, `icon`, `short`, `links.open` 입력
3. 필요하면 `summary`, `useCases`, `github`, `blog` 추가

이렇게 하면 별도의 HTML 수정 없이 카드와 모달이 자동 반영된다.

### 추천 파일 구조

```text
landing/
  ├─ landing.html
  ├─ landing.css
  ├─ landing.js
  └─ products.js
```

장기적으로는 `PRODUCTS`를 별도 파일로 분리하는 것이 가장 좋다.

이유:

* 새 앱 추가가 쉬워진다.
* 설명 데이터와 UI 로직이 분리된다.
* 유지보수가 단순해진다.

## 배포 제언

이 페이지는 정적 HTML/CSS/JS만으로 충분하다.

따라서 배포는 다음 두 방식이 모두 가능하다.

### GitHub Pages

적합한 경우:

* 빠르게 시작하고 싶을 때
* 정적 페이지로만 운영할 때
* 저장소 중심 공개가 목적일 때

### Cloudflare Pages

적합한 경우:

* 커스텀 도메인을 편하게 붙이고 싶을 때
* 추후 폼, 간단한 동적 기능, 리다이렉트 등을 붙일 가능성이 있을 때
* 제품 수가 계속 늘고 운영 유연성이 중요할 때

현재 요구사항을 기준으로는 둘 다 가능하지만, 장기적으로 제품이 계속 늘어날 예정이라면 Cloudflare Pages 쪽이 조금 더 유리하다.

---

## 요약

이 랜딩 페이지 초안의 핵심은 다음과 같다.

* 특정 하나의 앱을 메인으로 두지 않는다.
* `Workspace Hub`도 여러 앱 중 하나로 취급한다.
* 페이지는 앱 카탈로그 역할을 한다.
* 카드형 구조를 최대한 단순하게 유지한다.
* 앱별 상세 정보는 모달로 분리한다.
* GitHub, 블로그, 문서 링크를 앱별로 연결할 수 있게 한다.
* 새로운 앱은 데이터만 추가해서 확장할 수 있게 설계한다.

즉, 이 페이지는 단순한 소개 페이지가 아니라,
**계속 늘어나는 앱들을 정리해 보여주는 외부용 제품 허브**다.
